## Етап 3 — файли та повернення до списку

Причини збоїв, підтверджені кодом: підписання всіх файлів через material-photos; fallback до останнього сегмента URL втрачав папки; encoded URL-шлях не декодувався; lightbox і thumbnails використовували raw/public/expired URL напряму.

Нові файли:

- `src/utils/storageReference.js`: чистий розбір bucket/key; URL декодується один раз, raw keys не декодуються; bucket береться з Supabase URL або відомого префікса; папки зберігаються.
- `src/utils/storageUrl.js`: signed URL через поточну сесію без обходу Storage-політик.
- `src/components/StorageMedia.jsx`: завантаження, стан помилки й повтор, оновлення посилань раз на 50 хвилин, cleanup таймера та ігнорування застарілих відповідей.

Інтеграція: `AddressDetailsPage.jsx` — оригінали, звіти, матеріали, lightbox, download/share; `PhotoUploader.jsx` — previews і PDF-посилання; `WorkerPortal.jsx` — документи працівника. Віддалені URL іншого origin збережені як зовнішні посилання; їхні прострочені токени цей застосунок поновити не може.

`AddressListPage.jsx`: sessionStorage-стан окремо за user.id; пошук, усі фільтри, вкладка, число завантажених сторінок і scrollY. При поверненні сторінки завантажуються знову порціями по 40, зберігається глибина списку, а не старі копії записів. Додано стабільне сортування за id, захист від застарілих відповідей і пропуску сторінки після невдалого Load more.

Перевірено: unit-тести raw/public/sign/authenticated, вкладених папок, пробілів, percent/hash, зовнішніх URL і відхилення javascript URL; lint змінених JS/JSX; збірка.

Неперевірено: існування реальних об'єктів, доступ admin/worker, фактичні 403/404, поведінка download у різних браузерах, відновлення прокручування після реального переходу. Новий resolver навмисно не вгадує інший bucket при відмові доступу. Для public URL того самого Supabase також потрібна можливість підписати об'єкт поточною сесією; перевірити це перед впровадженням.

## Етап 5 — залишено відкритим

Повного аналізу OCR-шляху, змін OCR, порівняння старої/нової версії й міграцій у цій ітерації немає. Під час огляду інтеграції помічено: клієнт не показує needs_review/issues; truthy-перевірка суми губить 0; повторне сканування оновлює лише непорожні поля; нечіткий includes-match може вибрати неправильного білдера. Це кандидати для наступного етапу, не завершений OCR-аудит.

Після закриття попередніх етапів: простежити file→request→response→form→DB→worker; погодити контракт і правила ручного підтвердження; виправити мінімальні підтверджені розбіжності; окремо підготувати транзакційне збереження після отримання схеми; порівняти версії на знеособлених документах з еталонними значеннями. Платні виклики й записувальні перевірки — тільки після окремого погодження.
